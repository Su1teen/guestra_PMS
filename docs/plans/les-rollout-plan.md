# LES: доработка Guestra по отзывам клиента — план из трёх ходов

Клиент: LES Astana, LES Borovoe, баня «Тепло». Сейчас у них сторонние PMS, CRM и учётная система ресторана.
Цель: закрыть их сценарии в **существующих** Guestra CRM, PMS, n8n и AI Studio. Путь клиента
не перепроектируем, новых продуктов не создаём, дорабатываем то, что есть.

**Вне этого плана:**
- **Отдельная задача:** Channel Manager / Channex / OTA (аудит: `docs/plans/cm-channex-readiness.md`,
  ветка `claude/brave-pasteur-996334`).
- **Отдельная задача:** онлайн-оплата Kaspi / KPAY (`docs/plans/pay-kaspi-kpay.md`, ветка `claude/vigorous-pare-540e1f`).
- **Не планируем:** интеграцию с их текущей PMS и учётной системой ресторана, перенос данных, выгрузку старых чатов.

Банковские операции не автоматизируем: возврат, незаезд и штраф сотрудник вносит вручную, и каждая такая операция сохраняется в истории.

## 1. Принятые решения

| # | Решение |
|---|---|

## Ход 1. Чаты: доступ, распределение, Inbox, готовность к Meta, ручные шаблоны

Результат хода: менеджеры видят только своё, чаты делятся поровну, срочное наверху, а Meta можно подключить одной настройкой.

### 1.1 Права и разграничение по объектам (CRM)
- Роли: `sales_manager`, `sales_head` (РОП), `front_desk`, `property_manager`, `owner`, `service_staff` («Тепло»), `admin`.
  Права хранятся в справочнике, роль задаёт набор по умолчанию.
- Проверка на сервере для **каждого** маршрута: объект из `employee_properties` плюс право на действие. Начинаем с чатов, лидов, броней, платежей и отчётов.
- `GET /bootstrap` отдаёт только объекты сотрудника. Чаты и лиды переводим на постраничную выдачу с сервера: так канбан работает быстро, а данные не утекают.
- Журнал действий: смена статуса, ответственного, скидка, оплата.
- Управление пользователями: создать, заблокировать, сбросить пароль, требования к паролю, завершение сессий уволенного сотрудника.

### 1.2 Распределение чатов
- Новые поля и таблицы (аддитивная миграция): `employees.available_for_distribution`, график смены объекта
  (`shift_start` по умолчанию 09:00 Asia/Almaty), `conversation_assignments` (кто был, кто стал, кто назначил, причина, `operation_id`).
- **Пул для распределения** — чаты, которым нужен человек (R1), без ответственного, в объекте менеджера.
- **Утром:** в начале смены пул делится поровну между доступными менеджерами (100 / 4 = 25; 101 → 26/25/25/25).
- **Днём:** новый чат для человека получает менеджер с наименьшей нагрузкой за сегодня.
- **Кнопка «Передать чаты»** (РОП): выбор «все активные / непрочитанные / выбранные», распределение поровну между остальными. Повтор операции ничего не меняет. Автор продажи не меняется.
- Переключатель «На линии / Не на линии» у менеджера. Если менеджер не на линии, его новые чаты уходят остальным.
- Назначение атомарное: `UPDATE … WHERE assignee_id IS NULL`, чтобы два обработчика не отдали один чат двум людям.

### 1.3 Атрибуция продажи
- В лид добавляем `first_contact_employee_id`, `closing_employee_id`, `commission_employee_id`.
  Их фиксируем в момент, когда предоплата достигла 50%. Передача чата их не трогает.
- Перевести в «Успешно» может **любой** менеджер, у которого чат сейчас, а также РОП (это исправляет боль «закрыть может только первый»). Процент получает тот, кто закрыл.
- Если продажу целиком оформил ИИ и менеджер в ней не участвовал, `commission_employee_id` пустой, процента нет (R15).
  В отчётах менеджеров такие продажи — одна строка «Оформлено через Guestra», без отдельной аналитики по ИИ.

### 1.4 Inbox и канбан
- Вкладки объектов: Все / LES Astana / LES Borovoe / Тепло. Видны только доступные сотруднику.
- Блоки: **Новые** (нужен ответ, первый контакт), **В работе**, **Закрытые** (успешные и проваленные), **Избранное** (звёздочка у сотрудника).
- **Срочные:** отдельная колонка наверху. Признаки: ключевые слова («сегодня», «срочно», «через час», «ответьте»…) — редактируемый список для объекта; просроченный ответ; заезд сегодня или завтра. Бейдж можно снять вручную.
- **Повторное сообщение в закрытом чате:** чат поднимается в «Новые» с пометкой «Повторное обращение · бронь №…». Статус сделки (`won`/`lost`) не меняется, новый лид не создаётся. Исправление в `shared/inbox-attention.ts`.
- **Сообщение с задержкой:** если доставлено позже чем через 1 час после отправки, показываем пометку «пришло с опозданием» и настоящее время. Сортировка — по времени отправки.
- Канбан (Новые / В работе / Успешные / Проваленные): статусы переходят автоматически (ответили → «В работе», предоплата 50% → «Успешные»). Вручную — перетаскиванием или в один клик, с причиной для «Проваленные».

### 1.5 Готовность к Meta (WhatsApp Cloud API / WABA + Instagram)

**Исходное допущение (R13):** приложение Meta, WABA, номер и Instagram подключены напрямую к Guestra, мы управляем ими полностью.
Если у LES окажется провайдер (BSP), меняется только адаптер приёма и отправки, а не CRM.

**Архитектура (решено):** webhook Meta принимает **CRM**, а не n8n.

```text
Meta ──> CRM /webhooks/meta ──(подпись, запись, 200)──> provider_events
                                                      │  очередь BullMQ (воркер)
                                                      ▼
                         нормализация → дубль? → объект/гость → conversations/messages
                                                      │
                          нужен ИИ? ──> n8n Aidana ──> CRM outbound ──> Graph API ──> гость
                          нужен человек? ──> пул распределения (1.2)
```

Отправка гостю всегда идёт через CRM: n8n вызывает CRM, CRM — Graph API. Так сообщения не теряются при недоступности n8n, а ИИ и менеджеры пишут одним путём.

**Практики индустрии, на которые опираемся** (документация Meta и инженерные гайды провайдеров):
- Meta считает ошибкой любой ответ, кроме **200** (даже 202/204), и таймаут. Поэтому синхронно делаем только запись сырого события, остальное — в воркере.
- Неудачную доставку Meta повторяет, по распространённым данным, до 7 дней, затем событие теряется навсегда. Журнала доставок и повторной отправки у Meta нет. Значит, сохраняем каждое событие и следим за ошибками сами.
- Дубли бывают и от повторов, и потому, что Meta повторяет доставку всем приложениям, подписанным на аккаунт. Ключ идемпотентности — `provider + id` сообщения или статуса, храним не меньше 7 дней.
- Порядок не гарантирован: сортируем по `timestamp` из события.
- Побочные эффекты (лид, назначение, ответ ИИ) идемпотентны. Повторы по зависимостям разделены: сбой n8n не должен ломать приём.
- Проверка расхождений: периодическая задача сверяет необработанные события и сообщения без ответа.
- Webhook можно переопределить для **номера** или **WABA** (`webhook_configuration.override_callback_uri`; приоритет: номер → WABA → приложение).
  Так production и sandbox работают раздельно: у каждого свой номер и свой адрес, либо отдельное приложение Meta на каждое окружение.

**Окружения, чтобы ничего не развалилось:**
- **production:** реальные номер и аккаунт LES → `guestra_crm` production.
- **sandbox:** тестовый номер Meta for Developers (бесплатный) → `sandbox-crm`.
- **разработка и Studio:** эмулятор Meta, без сети.
- Секреты (`app_secret`, токен системного пользователя, verify token) у каждого окружения свои и хранятся только в переменных сервера.
- Флаг `META_ENABLED` на окружение: если он выключен, endpoint отвечает 404, а Studio и симулятор работают как сейчас.

**AI Studio остаётся полным тестовым стендом (R14):**
- Канал `simulator` идёт через **тот же** конвейер CRM (нормализация → распределение → n8n → шаблоны → отчёты), что и WhatsApp. Отличается только транспорт.
- Режим Studio «как WhatsApp» / «как Instagram»: Studio формирует подписанные события в формате Meta и отправляет их в CRM sandbox. Проверяются 24-часовое окно, шаблоны, статусы, реакции, сторис, задержки, дубли.
- Ответы гостю в этом режиме возвращаются в Studio, а не в Meta (транспорт `studio` в `channel_accounts`).
- Каждый сценарий плана (распределение, передача чатов, срочные, 90 минут, 50%, напоминание, штраф, отчёты) имеет сценарий в Studio.

Что делаем:
- Таблица `channel_accounts`: провайдер (`meta_cloud`, `studio`, позже `bsp`), `waba_id`, `phone_number_id`, `ig_user_id`, объект или пул объектов, ссылка на секрет, состояние. Сейчас одна запись на канал (R10).
- `POST /webhooks/meta` и `GET` для verify-token. Подпись `X-Hub-Signature-256` проверяем по сырому телу запроса, лимит размера.
- Таблица `provider_events`: сырое событие, статус обработки, попытки, ошибка, ограниченный срок хранения, dead-letter.
- В сообщениях: `provider_sent_at`, `received_at`, `event_type`, уникальность по `provider + external_message_id`.
- Разбор событий:
  - WhatsApp: текст, медиа, документы, аудио, статусы доставки (обновляют исходящее сообщение, лид не создают), реакции (не создают лид).
  - Instagram: Direct, ответ на сторис с текстом (это обращение), реакции и упоминания в сторис без текста (не лид), echo собственных сообщений.
- Отправка через Graph API (текст, шаблон, медиа) с учётом **24-часового окна WhatsApp**:
  вне окна отправляется только одобренный шаблон, и интерфейс это показывает.
- Справочник шаблонов WABA: имя в Meta, язык, переменные, статус одобрения. Связан с нашими шаблонами из 1.6.
- **Эмулятор Meta** для работы без ключей: скрипт и режим AI Studio отправляют подписанные тестовые webhook. Контрактные тесты: дубли, обратный порядок, задержка в 3 дня, всплеск сообщений, статусы, реакции.
- Страница «Каналы — диагностика» в CRM: последнее событие, задержка, ошибки, необработанные, повторить.
- Инструкция подключения: что запросить у LES, какие права нужны приложению, как заводятся токены. См. раздел «Подводные камни».

### 1.6 Ручной режим: панель «Шаблоны» в чате
- Одна кнопка в CRM Inbox, PMS Inbox и Studio (демо): выбрать шаблон → предпросмотр с подставленными данными брони → отправить.
- Шаблоны объекта: приветствие, предложение, подтверждение брони, счёт / реквизиты на оплату (документ из PMS), follow-up, напоминание за 48 часов, условия отмены, как добраться, ответ из базы знаний.
- Каждый шаблон связан с WABA-шаблоном для отправки вне 24-часового окна.
- Существующие ручные отправки (`offers/send`, `payment-requests/send`, `follow-ups/send`, `remind-now`) переносим в эту панель, сами отправки не переписываем.

### 1.7 n8n (Aidana, шлюз инструментов)
- Убрать зашитые `simulator` / `sandbox_les`: канал и объект берутся из входящего события.
- Новые ветки: `whatsapp` и `instagram` получают событие из CRM, а не от Meta.
- Передача человеку с кодом причины (`payment`, `corporate`, `barter`, `complimentary`, `discount`, `ai_unsure`, `guest_asked_human`) → попадает в пул распределения (1.2).
- По R16 ИИ на таких запросах не действует сам: отправляет гостю «Передаю ваш вопрос менеджеру, с вами свяжутся» (текст — шаблон объекта; ночью — «утром») и переводит чат в режим «нужен человек». Пока чат не вернули ИИ, он молчит.
- Шлюз инструментов отклоняет такие действия от ИИ на сервере, а не только по промпту.
- Подтверждение документа через ИИ (инструмент `confirm_document`) переносим сюда из плана запуска 3.
- Сначала sandbox, перед правкой — JSON-копия workflow.

### 1.8 Приёмка хода 1 (sandbox)
100 чатов / 4 менеджера → 25 каждому. Один менеджер ушёл → его чаты поделены на троих. Менеджер Астаны получает 403 на чат Борового через API.
Повтор webhook → одно сообщение. Задержанное сообщение → пометка «пришло с опозданием». Реакция → без лида.
Сообщение после успешной брони → «Новые», статус `won` сохранился. Ручная отправка каждого шаблона.
Запрос на бартер → ИИ передаёт менеджеру и замолкает; попытка ИИ вызвать запрещённое действие отклонена шлюзом.
Все сценарии проходят через Studio в режиме «как WhatsApp» без ключей Meta; с `META_ENABLED=false` Studio работает как раньше.
Регрессия сценариев запусков 1 и 2.

## Ход 2. Брони и деньги: удержание, разбивка пакета, отчёты, проценты, напоминание за 48 часов

Результат хода: РОП и руководитель видят в отчётах реальные деньги за день, процент менеджера считается автоматически.

### 2.1 Предварительная бронь до 90 минут (PMS — главный источник)
- Настройка объекта `holdMinutes` (по умолчанию 90, максимум 90) и `optionExpiryAction = cancel` для LES.
- Проверка истёкших опций каждую минуту (BullMQ repeatable), а не в ночном аудите. Отмена атомарная.
  Если истечение и оплата пришли одновременно, итоговое состояние одно.
- CRM больше не ставит свои 24 часа: срок берётся из PMS. В карточке и на шахматке показываем таймер.
- Оплата после истечения: деньги записываются, номер **не** восстанавливается сам. Менеджер получает задачу «Оплата после истечения брони».
- Статусы: предварительная → (≥ 50%) подтверждённая → проживает → выезд.

### 2.2 Разбивка пакета: проживание / питание / прочее и себестоимость
- Компонент тарифа получает основу начисления: `per_guest_per_night`, `per_guest_per_stay`, `per_stay`, `per_night`,
  а также цену для отчёта (`allocation_amount`) и себестоимость (`unit_cost`).
- Для LES: питание 4 000 ₸ **за гостя за ночь**, себестоимость 4 000 ₸. Дети младше 5 лет не считаются, с 5 лет — как взрослые
  (порог возраста — настройка объекта).
- При подтверждении брони сохраняется снимок разбивки: Проживание = цена пакета − Σ включённых компонентов. Суммы сходятся до тенге.
- Пересчёт при изменении числа гостей или дат — корректирующими строками, без перезаписи прошлого.
- Себестоимость — отдельная статья управленческого отчёта, проживание она второй раз не уменьшает.
- Категории дохода: Проживание, Питание (F&B), Баня, SPA, Прочее, Штрафы.

### 2.3 Отмены, незаезды, штрафы, возвраты (вручную)
- Кнопки в брони: «Отменить», «Незаезд», «Удержать предоплату как штраф», «Возврат», каждая с причиной и автором.
- Правило R5 подсказывает действие: при отмене позже чем за 24 часа до заезда система предлагает «удержать как штраф».
- Исходный платёж никогда не удаляется: возврат — отдельная строка с датой возврата.

### 2.4 Напоминание за 48 часов
- Заменяем `pre_arrival_3d` / `pre_arrival_1d` на `pre_arrival_48h` для LES (набор напоминаний — настройка объекта).
- Текст: даты, время заезда, номер брони, номера/категории, **оплаченная** сумма, крайний срок изменения (T−24h), условие о сгорании предоплаты.
- При изменении дат старое напоминание отменяется и создаётся новое. Для отменённой брони не отправляется.
  Если бронь создана позже T−48h, напоминание не отправляется (подтверждение уже ушло).
- Отправка вне 24-часового окна — через WABA-шаблон. Кнопка «Отправить сейчас» из панели шаблонов.

### 2.5 Отчёты (CRM, данные из PMS)
Один серверный контракт отчётов в PMS. CRM его показывает. В CRM ничего не пересчитываем.

**«День в день» (главный экран РОП)** — по дате оплаты, в часовом поясе объекта. Предлагаемые колонки (подтвердить, Q4):

| Дата | Новых броней (шт.) | Предоплаты по будущим заездам | Оплаты проживающих и доплаты | Штрафы | Возвраты | **Итого поступило** |
|---|---|---|---|---|---|---|

- Отменённые брони в отчёт не попадают. Удержанная предоплата попадает в «Штрафы».
- Над таблицей — карточки итогов за период и график по дням.
- «Подробнее» по строке: брони, гость, менеджер, сумма, сколько оплачено, разбивка проживание/питание.
- Выгрузка: Excel (итоги и подробности отдельными листами) и PDF / печать.

**Проценты менеджеров** — за период: менеджер | проживание с оплат за период (включая предоплату) | ставка | процент.
Детализация по кнопке. Баня — отдельная строка со своей ставкой. Комплиментарные, «для шефа» и штрафы исключены.
Продажи без менеджера — строка «Оформлено через Guestra» без процента (R15).

Образца Excel от клиента нет: собираем качественную версию по этому описанию и дорабатываем с LES после показа.
Ставки — настройка объекта (по умолчанию 10%).

**Управленческий отчёт** — вместо демо-данных CRM:
Доходы (Проживание, Питание, Баня, SPA, Прочее, Штрафы) → Себестоимость (питание поставщика и другие статьи по отелю) → Расходы (вводятся вручную, уже есть `management_inputs`) → Результат.
Колонки: План | Факт | Отклонение | Прошлый период. Если затраты не заполнены, пишем «не заполнено», а не 0.

**Конструктор шаблонов отчётов** (сохранённые настройки отчёта):
выбор отчёта → период (сегодня / неделя / месяц / свой) → фильтры (объект, менеджер, канал, тип номера, категория, статус) → группировка → колонки → «Сохранить как…».
Шаблон хранит настройки, а не цифры: при открытии данные свежие. Доступ: «только мне / моей команде / руководству».

**Внешний вид:** единый визуальный стиль, крупные итоговые цифры, понятные подписи без жаргона, пустые и ошибочные состояния, удобная версия для телефона, печать на A4.

### 2.6 n8n
- Агент знает правило оплаты: при 50% бронь подтверждается, ИИ сообщает гостю и передаёт сотруднику, если нужен счёт.
- Инструмент «условия отмены» для ответа гостю на основе R5 и настроек объекта.

### 2.7 Приёмка хода 2
Бронь без оплаты → через 90 минут номер свободен. Оплата одновременно с истечением → одно итоговое состояние.
Пакет 100 000 на 2 гостей → проживание 92 000, питание 8 000, себестоимость 8 000, процент 9 200. Оплата 14-го при брони 13-го → в отчёте 14-е.
Отмена за 12 часов до заезда → штраф. Перенос дат → новое напоминание за 48 часов. Итоги в Excel совпадают с экраном.

## Ход 3. Цены, шахматка, гость, база знаний ИИ

### 3.1 Упрощённый календарь цен (PMS, просмотр в CRM)
- Экран «Календарь цен»: базовая цена по типу номера, **мин. и макс. цена**, кнопки «+ Сезон», «+ Праздник», «+ Акция» (название, даты, типы номеров, % или фиксированная цена).
- Порядок применения: ручная цена на день → праздник → сезон → база → одна акция → ограничение мин./макс.
- Календарь показывает итоговую цену дня и подсказку «почему такая цена». Предпросмотр перед применением, журнал изменений.
- Хранение поверх `rate_restrictions.rateOverride`. Уже подтверждённые брони не пересчитываются.
- Расчёт цены — только сервер PMS. CRM и ИИ берут цену оттуда.

### 3.2 Шахматка
- Линия «Сегодня» в часовом поясе объекта.
- Переключатель «История»: выехавшие, отменённые, незаезды видны полупрозрачными, по клику — карточка только для чтения. Номер они не занимают.
- Цвета с бейджами (не только цветом): предварительная с таймером, подтверждённая, проживает, не работает / ремонт (серые с разными значками), история. Перед этим — аудит текущей палитры.
- Завершённую бронь и её платежи задним числом обычный сотрудник не меняет. Исправление — отдельной операцией с аудитом.

### 3.3 Гость: история, лояльность, комплиментарные, бартер
- Карточка гостя (Guest 360): все чаты, брони, оплаты, услуги по объектам, доступным сотруднику.
- Поиск: телефон, ФИО, номер комнаты (только вместе с объектом и активным проживанием), затем сверка документа.
- Уровень гостя: обычный / постоянный / VIP. Привилегии — атрибут гостя, а не автоматическая скидка.
- **Комплиментарное** и **бартер** — тип цены брони с причиной, контрагентом и тем, кто разрешил. Доступно только по праву.
  В отчётах — 0 ₸ дохода, но себестоимость и ночь учитываются, в процент не входит.
- Скидки «для шефа» и маркетинговые — с причиной; в отчётах уменьшают нужную категорию.

### 3.4 База знаний ИИ
- Структура `property_knowledge` по темам: номера и вместимость, что входит в цену, питание, баня, правила заезда и выезда, отмена и предоплата (R5), дети, животные, как добраться, акции. Сущности, которые меняются (цены, свободные номера, акции), агент берёт **через инструменты PMS**, а не из текста.
- Инструменты агента в n8n: `get_knowledge(topic)`, `get_price_calendar`, `get_cancellation_terms`, `get_guest_history`.
- Правило агента: не знает ответа или данные противоречат друг другу → уточняет у гостя или передаёт человеку с причиной `ai_unsure`. Не выдумывает.
- Редактор базы знаний в CRM: темы, текст, кнопка «проверить ответ ИИ» (через Studio).

### 3.5 AI Studio (демо)
- Каналы «WhatsApp» и «Instagram» в симуляторе через эмулятор Meta из 1.5: на демо видно окно 24 часа, шаблоны, статусы доставки, реакции.
- Сценарии для показа: ночной поток и утреннее распределение, оплата 50%, напоминание за 48 часов, отмена со штрафом.

### 3.6 Приёмка хода 3
Сезон и праздник на одну дату → цена предсказуема, причина видна. История в шахматке не блокирует продажу.
Гость по номеру комнаты без активного проживания не находится. Комплиментарная бронь → 0 дохода, ночь учтена.
ИИ на вопрос вне базы знаний → уточняет или передаёт человеку.

## Подводные камни Meta (выявить до получения ключей)

1. **Один callback URL на приложение** для каждого типа объекта. Если сейчас webhook направлен в их старую CRM, при переключении старая система перестанет получать события. Нужен план переключения.
2. **Повторная доставка:** если сервер не ответил, Meta повторяет доставку ещё несколько дней. Отсюда, вероятно, их «сообщения 2–3-дневной давности». Решение — быстрый ответ 200 и защита от дублей.
3. **Порядок не гарантирован:** сортируем по времени отправки у Meta, а не по времени прихода webhook.
4. **24-часовое окно WhatsApp:** вне окна — только одобренные шаблоны. Шаблоны нужно заранее подать на модерацию; одобрение занимает время, бывают отказы.
5. **Номер WhatsApp:** если он сейчас в приложении WhatsApp Business или у другого провайдера (BSP), нужен перенос либо режим совместной работы (coexistence). Проверить, где номер сейчас.
6. **Токены:** нужен постоянный токен системного пользователя Business Manager, а не временный токен разработчика. Хранить только на сервере, с ротацией.
7. **Instagram:** профессиональный аккаунт, связанная страница Facebook, права приложения на сообщения (может понадобиться App Review), включённый доступ к сообщениям в настройках Instagram. Окно ответа тоже ограничено.
8. **Медиа:** ссылки Meta на файлы временные. Скачиваем к себе сразу.
9. **Лимиты отправки** (уровни сообщений) и качество номера: массовые рассылки шаблонами могут понизить рейтинг.
10. **Типы событий:** статусы, echo, реакции, упоминания в сторис, редактирование и удаление — ни одно из них не должно создавать лид.
11. **Сопоставление гостя:** WhatsApp даёт телефон, Instagram — только IG-id. Профили объединяем вручную или после подтверждения.
12. **Тестовая среда:** приложение Meta for Developers даёт тестовый номер WhatsApp. На нём можно пройти путь целиком до получения ключей LES.
13. **История чатов при подключении номера:** в режиме coexistence Meta может перенести до 6 месяцев личных переписок, но **только один раз, при подключении** (отель при подключении выбирает «поделиться чатами»). Если пропустить, повторить можно лишь через отключение и повторное подключение номера. Решить до подключения.
14. **Только 200:** любой другой ответ webhook Meta считает ошибкой и повторяет. Отсюда ещё одна возможная причина дублей и «старых» сообщений у LES.
15. **Несколько приложений на одном WABA:** если к аккаунту LES подписана и старая CRM, и Guestra, сбой одного приложения даёт повторы обоим. На время переключения учитываем это при защите от дублей.

- **CRM:** роли и права, `conversation_assignments`, доступность сотрудника и смены, атрибуция в `leads`, `channel_accounts`, `provider_events`, поля сообщений, избранное, шаблоны, сохранённые отчёты.
- **PMS:** `holdMinutes`, основа начисления, цена для отчёта и себестоимость у компонентов, снимок разбивки брони, правила календаря цен, тип цены брони (комплиментарное / бартер), ставки процентов.

Каждая миграция вносится в политику миграций. Юнит-тесты (CRM — PGlite, PMS — Postgres-спеки), e2e на sandbox, регрессия запусков 1 и 2.
