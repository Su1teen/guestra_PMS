# Удалённая предоплата брони LES

## Что есть в текущем коде

- PMS хранит параметры гарантии и опции. `ReservationGuaranteeService` записывает ручную предоплату и подтверждает бронь при покрытии гарантии. Connect v2 пока создаёт бронь со статусом `assigned`, а в CRM предложение v2 сохраняется с `deposit: 0`.
- CRM v2 проверяет личность, принадлежность брони, согласие из чата и фиксирует результаты команд PMS. Ручные коммерческие платежи CRM используют отдельный путь. Для броней, которыми владеет PMS, CRM читает проекцию PMS.
- n8n вызывает CRM, CRM подписывает команды PMS. В AI Studio виртуальные WhatsApp и Telegram используют транспорт `simulator`. Имеющаяся симуляция платежа сценария явно помечена `ledgerEffect=false`.

## Порядок реализации

1. Добавить клиент тестовых счетов на номер телефона в PMS и проверку подписи webhook на исходных байтах. Хранить ключи на сервере. Проверять режим, телефон, сумму целыми тенге, идентификатор и ссылку счёта. При неизвестном результате создания сверять исходную операцию до новой попытки.
2. Под отдельной настройкой объекта создать в Connect v2 путь бронирования с опцией. Использовать параметры PMS и согласованные гостем цену и условия. Для LES предоплата подтверждает бронь при достижении гарантии. Действующие пути без удалённой оплаты сохраняют прежнее поведение.
3. Создавать платёжное намерение до запроса провайдеру. Сохранять область объекта, бронь, сумму, валюту и устойчивый ключ идемпотентности. Записывать внешний ID счёта и результат сверки. После подписанного `paid` сверять счёт у провайдера, один раз отражать тестовую предоплату в изолированной БД и подтверждать только действующую опцию. Позднюю оплату после отмены или смены условий сохранять для разбора сотрудником с исходным счётом и суммой.
4. В CRM v2 использовать свойство, клиента, переписку и подтверждение из текущего диалога. Размер счёта определяет PMS. Номер берётся из подтверждённого номера для оплаты. Если он неизвестен, агент спрашивает. После read-back CRM добавляет в переписку подтверждённую ссылку. Оплату и статус отображать из PMS, обновления переписки передавать обычным транспортом.
5. Подключить инструмент в sandbox workflow Aidana. AI Studio использует тот же CRM-контракт через виртуальные каналы. В тестах провайдер возвращает тестовую ссылку и подтверждает оплату симуляцией. Фактическую доставку push в Kaspi можно проверить только на live после отдельной активации.
6. Сначала пройти локальные и CI-проверки, затем прогнать связку на Railway sandbox с отдельным тестовым гостем. После успешного прогона слить изменения и повторить smoke на актуальных ревизиях. Флаг включать только в sandbox.

## Проверки

| Случай | Ожидаемое поведение |
| --- | --- |
| Подтверждённое предложение, номер, действующая опция | Один счёт, ссылка в чате, бронь ожидает предоплату |
| Повтор сообщения, команды или ответа провайдера | Повторно используется тот же счёт, одна запись оплаты |
| Чужая бронь, истёкшая цена, ручной режим, нет согласия | Счёт не создаётся |
| Номер отсутствует или неверный, сумма дробная | Запрос корректного номера или передача сотруднику для разбора суммы |
| Ошибка провайдера, таймаут, лимит | Статус ошибки или неизвестного результата, без второго счёта наугад |
| Неверная подпись, другая валюта, режим или сумма | Финансовое состояние не меняется |
| События оплачено, ошибка, истёк, отменён | Только сверенный `paid` влияет на гарантию действующей брони |
| Оплата после снятия опции | Видна сотруднику для разбора, отменённая бронь не восстанавливается автоматически |
| Тест по виртуальному WhatsApp и Telegram | Ссылка и статус отображаются в правильной переписке в Studio и CRM |

В QUT Pay выделить до 5 уникальных счетов на основной прогон. Повторы, конкуренцию, ошибочные подписи, несовпадение суммы и исключения проверять на имитации HTTP и локальных фикстурах. При повторной проверке после merge общий предел — 10 уникальных счетов.

## Включение sandbox

- Обработчик PMS принимает события на `/api/v1/webhooks/qutpay`. Зарегистрировать его в QUT Pay для `invoice.paid`, `invoice.failed`, `invoice.expired`, `invoice.cancelled`. После получения секрета добавить `QUTPAY_WEBHOOK_SECRET` и включить `QUTPAY_SANDBOX_PREPAYMENTS_ENABLED` только в `sandbox-pms`.
- В CRM разрешить sandbox-принципалу n8n `tool:create_remote_prepayment`. Просьбу о счёте привязать к входящему сообщению, в котором гость указал номер. После доставки предложения дождаться явного согласия. CRM сверяет номер и сумму перед отправкой подписанной команды. Ссылку брать из ответа команды и отправлять через обычный `outbound/prepare` и подтверждение доставки. Оплаченную бронь перепроверять через PMS.
- В AI Studio разрешить инструмент в конфигурации sandbox-агента. Для теста WhatsApp и Telegram использовать синтетические номера, один случай успешной предоплаты, один истечения, один отказа и один платёж после отмены. Резерв пятого счёта оставить на восстановление после неопределённого результата.
