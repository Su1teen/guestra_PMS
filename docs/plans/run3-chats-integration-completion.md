# Запуск 3 — доводка чатов и связки PMS ↔ CRM ↔ AI Studio ↔ n8n

Цель: снять все ограничения запуска 2. Чаты работают по всем каналам на sandbox и в production. ИИ сам распознаёт подтверждение документа. Почта и SMS реально уходят и приходят. Деплой не ломается.

Основа: PR Su1teen/guestra_PMS#25, Su1teen/guestra_crm#9, Su1teen/guestra_ai_studio#7 (смёржить первыми, CRM раньше PMS и Studio).

## 0. Что выяснено (состояние на 2026-11-11)

**Railway**, проект `guestra(AI + PMS + CRM)`:

| Окружение | PMS | CRM | Studio | Базы |
|---|---|---|---|---|
| sandbox | `sandbox-pms` | `sandbox-crm` | `sandbox-studio` | своя Postgres у каждого + Redis |
| production | `haip-demo` | `guestra_crm` | `guestra_ai_studio` | своя Postgres у каждого + Redis |

**n8n** (`n8nion8n-production-57b1`): наши только workflow с префиксом `guestra` / `GUESTRA-STUDIO`. Остальные — другие проекты; их не трогаем и не читаем.

| Workflow | Роль | Замечания |
|---|---|---|
| `GUESTRA-STUDIO · Aidana Agent (sandbox / prod)` | Входящее из Studio → claim → CRM inbound → CRM context → сборка промпта → агент с 9 инструментами → CRM outbound prepare/result → подписанные callback | Канал зашит `simulator`, свойство `sandbox_les` |
| `GUESTRA-STUDIO · CRM tool gateway (sandbox / prod)` | Единственный путь инструментов к CRM | Проверяет `allowedActions` из контекста CRM; ключ CRM — n8n credential |
| `GUESTRA-STUDIO · Signed callback`, `Error & Recovery`, `Capabilities` | Служебные | Без изменений |
| `Guestra CRM Telegram Guest Agent` (активен) | Реальный Telegram-бот → **production** CRM по старому API v1 | Плюс webhook `guestra-telegram-outbound` для ответов сотрудников |
| `guestra_PMS_test` | Старый демо-бот на старых адресах | Кандидат на отключение |

**Найденные проблемы:**
1. **Telegram-бот в production работает вполсилы.** CRM с `CRM_PMS_INTEGRATION_ENABLED=true` отвечает `409 PMS_V2_REQUIRED` на его инструменты v1 (поиск, предложение, бронь, услуги). Бот может только разговаривать.
2. **«Да» на документ распознают правила CRM, а не ИИ.** В ИИ-чате возможен двойной ответ: подтверждение от CRM и ответ агента.
3. **Почта и SMS в sandbox не уходят:** провайдеры не настроены. Входящей почты нет: нет relay.
4. **В production PMS выключен вход сотрудников** (`AUTH_ENABLED=false`). Inbox там по дизайну не откроется: доступ без входа разрешён только в sandbox.
5. **Ключи CRM неизменяемы:** новые права = новый ключ. В sandbox остались неиспользуемые `pms-inbox`, `studio-read`, отозванный `studio-read-v2`. В production у ключей Studio и PMS нет прав `inbox.*` / `agent.write` для новых функций.
6. **Деплой хрупкий:**
   - рабочие копии CRM и Studio в CRLF ломают контрольные суммы миграций;
   - смена переменной без `--skip-deploys` пересобирает сервис из `main`;
   - CLI в папке Studio привязан к другому проекту.
7. **Мусор от ошибочного деплоя:** пустой проект `guestra_ai_studio` с упавшим деплоем `a22d484e` и доменом `guestraaistudio-production.up.railway.app`.
8. **Мелочи:**
   - в PMS нет фильтра «Мои / Без ответственного»: сотрудники PMS не связаны с сотрудниками CRM;
   - копия письма в CRM — без повторов (best-effort);
   - в CRM Inbox не виден статус документа.

## 1. Решения, которые нужны от вас до старта

| # | Вопрос | Варианты |
|---|---|---|
| D1 | Почта | SMTP своего домена, SendGrid, Mailgun или SES (PMS поддерживает все). Нужны адрес отправителя и доступ. |
| D2 | SMS | Twilio, Infobip, Vonage или Bird (поддерживаются). Нужен аккаунт с отправкой на номера KZ. Можно отложить. |
| D3 | Входящая почта | Ящик отеля по IMAP (n8n читает и передаёт в CRM) или inbound-webhook провайдера (Mailgun Routes / SendGrid Inbound Parse). Нужны доступы к ящику или провайдеру. |
| D4 | Вход сотрудников в production PMS | Включить `AUTH_ENABLED=true` с Keycloak/OIDC; или пока не открывать Inbox в production. Отдельно нужно решить, держать ли production открытым без входа: это и сейчас риск. |
| D5 | Production Telegram-бот | Перевести на общий v2-конвейер Aidana (рекомендую) или оставить как есть до отдельного решения. |
| D6 | Изменения в n8n | Разрешаю менять только `GUESTRA-STUDIO · *` и `Guestra CRM Telegram Guest Agent`: сначала sandbox, после проверки prod. Перед правкой сохраняю JSON-копию. |

Безопасность: ключ n8n API был передан в чате. После работ его стоит перевыпустить. В репозитории и файлах проекта он не хранится.

## 2. План работ (один заход, по порядку)

### Этап A. Гигиена и деплой

1. **A1.** `.gitattributes` в CRM и Studio (`* text=auto eol=lf`, `*.sql eol=lf`), чтобы рабочие копии всегда были в LF. Скрипт `ops/railway/deploy-sandbox.mjs` для каждого репозитория:
   - проверяет, что нет CRLF;
   - деплоит с явными `--project`, `--service`, `--environment`;
   - никогда не меняет переменные без `--skip-deploys`.
2. **A2.** Смёржить PR #9 (CRM) → #25 (PMS) → #7 (Studio). Дальше sandbox собирается из `main`, переменные можно менять без падений.
3. **A3.** Вы вручную удаляете проект `guestra_ai_studio`: деплой `a22d484e` и домен.
4. **A4.** Отозвать неиспользуемые ключи CRM в sandbox (`pms-inbox`, `studio-read`). Отзыв — единственное разрешённое изменение старого ключа.

### Этап B. ИИ сам распознаёт подтверждение документа

**B1. CRM:**
- Контекст `/v2/context` получает `pendingDocument`: id, тип, номер брони, ссылка, когда отправлено, режим.
- Если документ ждёт ответа, в `allowedActions` появляется `confirm_document`.
- Новый инструмент `confirm_document`, `POST /v2/document-confirmations/:id/guest-answer`, принимает `{ outcome: confirmed | declined | question, inboundMessageId }`. Сервер проверяет, что сообщение входящее, из этого чата и пришло после запроса документа. Тогда документ подтверждается или отмечается отклонённым; в PMS — `detailsConfirmedBy = ai`.
- Права: `agent.write` + `tool:confirm_document`, тот же механизм, что у `book_accommodation`.

**B2. CRM, разделение ролей:**
- В ИИ-чатах правила больше не подтверждают и не отправляют своё сообщение. Решает агент, а ответ гостю пишет он сам, поэтому двойного ответа нет.
- Правила остаются для ручных чатов, email и SMS (там ИИ нет). И как страховка: если ИИ не ответил за N минут, а ответ гостя — однозначное «да», документ подтверждается по правилам.

**B3. CRM.** Новый ключ `n8n-service-v2`: права текущего ключа n8n плюс `tool:confirm_document`. Старый не трогаем до переключения.

**B4. n8n sandbox:**
- **Credential.** Новый credential с ключом `n8n-service-v2` через API, подключить его к HTTP-узлам Aidana и шлюза.
- **Шлюз.** Новый вариант `confirm_document` → `POST /v2/document-confirmations/:id/guest-answer`; добавить в карту TOOLS и в «Shape result».
- **Агент.** Новый tool-узел `confirm_document` (параметры от ИИ: `outcome`; `inboundMessageId` — из «Normalize CRM inbound»).
- **Build agent prompt.** В факты добавить `ожидающий_подтверждения_документ`. В правила — короткую инструкцию:
  - если гость однозначно подтвердил документ → вызвать `confirm_document` с `confirmed` и поблагодарить;
  - если просит изменить → вызвать с `declined` и передать сотруднику;
  - если задаёт вопрос → ответить и не подтверждать.
- Перед правкой — JSON-копия workflow. Изменения только через n8n API, workflow остаётся активным.

**B5.** Те же правки в prod-версиях — после того как сквозной тест sandbox пройдёт.

### Этап C. Почта и SMS по-настоящему

1. **C1. Исходящая почта** (решение D1). Переменные провайдера в `sandbox-pms`, затем в production. Проверить заголовки, адрес отправителя и SPF/DKIM домена (если SMTP своего домена).
2. **C2. Исходящие SMS** (решение D2), переменные провайдера.
3. **C3. Входящая почта** (решение D3). Новый n8n workflow `guestra-email-inbound (sandbox / prod)`:
   - IMAP Email Trigger или webhook провайдера → нормализация (отправитель, тема, текст без цитат, Message-ID) → `POST /v2/inbox/email/inbound`;
   - для этого новый ключ CRM `email-relay` с правом `email.inbound`.
   - Ответ гостя на письмо с документом попадает в тот же email-чат и распознаётся правилами (B2).
4. **C4. Копия писем PMS → CRM надёжно.** Вместо best-effort — очередь с повторами (BullMQ/outbox PMS), идемпотентный ключ уже есть.

### Этап D. Каналы-мессенджеры

1. **D-1. Production Telegram** (решение D5). Перевести `Guestra CRM Telegram Guest Agent` на v2-конвейер Aidana:
   - Telegram Trigger → CRM inbound (канал `telegram`) → контекст v2 → тот же агент и шлюз;
   - у шлюза параметризовать канал и property вместо зашитых `simulator` / `sandbox_les`;
   - ответ → Telegram → CRM outbound result.
   - Ответы сотрудников уже идут через webhook `guestra-telegram-outbound` (в production CRM он настроен).
2. **D-2. Sandbox Telegram** (по желанию). Тестовый бот и `AGENT_OUTBOUND_WEBHOOK_URL` в `sandbox-crm`, чтобы проверять реальный мессенджер, не трогая production.
3. **D-3. WhatsApp.** Транспорт в CRM уже есть (`WHATSAPP_OUTBOUND_WEBHOOK_*`); нужен провайдер и workflow. Отдельное решение, не в этом заходе.

### Этап E. Production-раскатка

1. **E1. Ключи CRM в production:** `pms-inbox-v2` (+`inbox.write`) и `studio-v3`. Сначала проверить, каким ключом сейчас ходит production Studio, и сохранить его права. Плюс `n8n-service-v2` и `email-relay`.
2. **E2. Флаги PMS в production:** `GUESTRA_INBOX_ENABLED=true` — только после решения D4. Флаг sandbox-сотрудника в production не работает по коду.
3. **E3.** После каждого шага — health, лог проверки перед деплоем, smoke-проверка Inbox.

### Этап F. Доводка интерфейсов

1. **F1. Сотрудники PMS ↔ CRM.** Связка по email, `staffReference` → `assigneeId` в CRM. В PMS появляются фильтры «Мои / Без ответственного» и назначение ответственного.
2. **F2. CRM Inbox:**
   - статус документа на сообщении;
   - кнопка «Гость подтвердил»;
   - отправка документа из CRM, как в PMS: CRM просит у PMS подписанную ссылку командой.
3. **F3. AI Studio.** Ссылки в сообщениях кликабельны; бейдж статуса документа в чате отеля.
4. **F4. Документ файлом** (по желанию). PDF-вложение в email (письмо уже содержит полный HTML). В мессенджерах остаётся ссылка: она работает везде без медиа-хранилища и сканера.

## 3. Проверка (критерии готовности)

**Sandbox, сквозные сценарии:**
1. Документ через ИИ → гость в Studio: «А завтрак входит?» → ИИ отвечает и не подтверждает.
2. Гость: «Да, всё верно» → ИИ вызывает `confirm_document` → в брони PMS «Гость подтвердил (ИИ)». Сообщение гостю ровно одно.
3. Документ вручную → «Нет, даты другие» → чат в «Фокусе» сотрудника, в брони без подтверждения.
4. Документ по email → письмо реально приходит → ответ «Да» с ящика гостя → через n8n IMAP попадает в email-чат → бронь подтверждена.
5. SMS реально приходит на тестовый номер.
6. Ответ сотрудника из PMS в email-чат приходит гостю.
7. Регрессия: сценарии запуска 1 (48) и запуска 2 (20).

**Production (после D4/D5):**
- smoke Inbox;
- Telegram: поиск → предложение → «Да, бронируйте» → бронь в PMS;
- ответ сотрудника из PMS приходит в Telegram.

Юнит-тесты на всё новое (CRM PGlite, PMS, Studio). CI зелёный во всех трёх репозиториях. Миграции в политиках.
