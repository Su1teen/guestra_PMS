# Обратная связь пилота, раунд 2 (front + back office)

Источник: интервью с сотрудником, который работает и на ресепшене, и в бэк-офисе.
Объём: не минорные правки, а доработка ключевых потоков бронирования, документов и
внешнего вида. PMS остаётся главной системой (operational authority), CRM должна
работать по той же логике.

> База знаний `kb/HAIP_KNOWLEDGE_BASE.md` в этом рабочем дереве отсутствует (каталог в
> `.gitignore`). Всё, что ниже помечено «решает отель», — настройки, а не зашитые
> правила. Нерешённые вопросы — в конце документа.

## 1. Детские возрастные категории и цены

**Модель.**
- Настройка объекта `childAgeBands`: список категорий `{ code, label, minAge, maxAge, occupiesBed }`.
  По умолчанию из интервью: `0–5`, `6–12`. Старше верхней границы — взрослый.
- Тариф: `child_supplements jsonb` — по каждой категории **массив сумм по порядку ребёнка**
  (`[0, 3000, 5000]` = первый бесплатно, второй 3000, третий и далее 5000 за ночь).
  Так покрывается «сумма меняется с каждым ребёнком и категорией». Пусто → старое поведение
  через `extra_child_amount`.
- Бронь: `child_ages smallint[]` (возраст на дату заезда). `children` остаётся и считается
  из длины массива — обратная совместимость для OTA/Connect, которые шлют только число.

**Расчёт** (`canonical-room-pricing.ts`): дети сортируются по категории, каждому
начисляется сумма по своему порядковому номеру. Взрослые заполняют включённые места
первыми (как сейчас). Детям категории с `occupiesBed=false` место не нужно и они не
участвуют в проверке `maxOccupancy`. Результат возвращается с разбивкой
`supplements[] = { band, ordinal, amountPerNight }`, чтобы её видели квота, мастер брони,
подтверждение и счёт.

**UI.** В мастере брони и в составе гостей: «Дети» → для каждого ребёнка выбор возраста;
под ценой — строки «Ребёнок 6–12 (2-й) · 3 000 × 3 ночи». Настройки тарифа — таблица
«категория × порядок ребёнка».

**Миграция:** аддитивная `0045`, null = текущее поведение. Тесты: расчёт по категориям и
порядку, обратная совместимость без возрастов, вместимость с младенцами.

## 2. Цена за ночь и число гостей в документах (PDF)

- **Подтверждение / предложение:** таблица по ночам (дата, номер, тариф, сумма, налог),
  состав: «2 взрослых, 2 ребёнка (4 и 9 лет)», доплаты за детей отдельной строкой.
- **Счёт / выписка фолио при выезде** (новое): `GET /v1/folios/:id/statement` — HTML для
  печати с теми же разделами: гость, номер, даты, гости, проживание по ночам,
  услуги, платежи, баланс. Кнопка «Счёт (PDF)» в модалке выезда и в фолио; после
  выезда — «Отправить счёт на email» (через существующий EmailService, с аудитом).
- PDF делается печатью браузера (`@media print`, A4) — как уже работает подтверждение,
  без новых зависимостей и серверного Chromium.

## 3. Карточка брони при наведении в шахматке

Всплывающая карточка (задержка ~250 мс, также по фокусу с клавиатуры, не перекрывает
курсор): гость и телефон, даты и число ночей, категория / номер / тариф, взрослые и дети
с возрастами, статус (в т.ч. «не подтверждена, опция до …»), итог / оплачено / долг,
источник, группа, особые пожелания. Данные берутся из уже загруженных броней и
ledger-запроса шахматки — без запроса на каждое наведение. Компонент общий для
шахматки и списка.

## 4. Групповая бронь

- **Мастер «Групповая бронь»** (шахматка и список броней): заказчик (гость или компания из
  профилей), название группы, даты, строки «категория × количество × тариф × гости на
  номер», общий расчёт, опция и предоплата для всей группы.
- **API:** `POST /v1/bookings/group` — одна транзакция под inventory lock: одна `booking`
  (`group_name`, `group_profile_id`), N резерваций, всё или ничего, идемпотентность по
  `requestId`, канонический расчёт каждой строки, проверка ожидаемой суммы.
- **Работа с группой:** в drawer — вкладка «Группа» со всеми номерами, массовые действия:
  подтвердить, отправить подтверждение, назначить номера, отменить; в шахматке —
  метка группы на плашках и подсветка всех номеров группы при наведении.
- Имена гостей по номерам можно внести позже (rooming list уже есть для блоков —
  переиспользуем импорт). Большие контрактные группы остаются в блоках (allotment).

## 5. Подтверждение брони

Типовой процесс в PMS: бронь создаётся **предварительной (опцией)** со сроком; гостю
уходит предложение с суммой предоплаты; при поступлении гарантии (предоплата / карта /
гарантийное письмо компании) бронь становится **подтверждённой** и гостю автоматически
уходит подтверждение; если к сроку гарантии нет — опция снимается и номер освобождается
(или сотрудник получает напоминание — решает отель).

**Изменения:**
- Staff-создание, `addRoom` и групповая бронь создают `pending` («Не подтверждена»).
  Поля (миграция `0045`): `option_until timestamptz`, `guarantee_type`
  (`deposit | card | company | none`), `required_deposit numeric`, `confirmed_at`,
  `confirmed_by`, `confirmation_sent_at`.
- Срок опции по умолчанию и правило истечения — настройки объекта
  (`optionHoldHours`, `optionExpiryAction: 'cancel' | 'notify'`).
- Подтверждение:
  - **автоматически**, когда сумма платежей и депозитов по брони достигает
    `required_deposit` (по умолчанию `depositPercentage` от суммы проживания; 0 → любой
    платёж); хук в местах записи платежа / депозита, в той же транзакции;
  - **вручную** кнопкой «Подтвердить» с типом гарантии; `none` — только с причиной и
    правом `reservations.write`, пишется в аудит.
- При переходе в `confirmed` — событие `reservation.confirmed` (outbox) и автоотправка
  подтверждения гостю (email; SMS, если настроен), `confirmation_sent_at`, аудит.
  Автоотправку можно выключить в настройках.
- Истечение опции — cron (`night-audit`/scheduler): `cancel` → отмена с причиной
  «Истёк срок опции», освобождение инвентаря, письмо гостю; `notify` → staff-уведомление.
- OTA / GDS / Connect с гарантией канала и онлайн-оплата booking engine остаются
  `confirmed` сразу — текущее поведение каналов не меняется.
- Видимость: в шахматке неподтверждённые — штриховка и метка срока; фильтр
  «Не подтверждены»; на главной — «Опции истекают сегодня» и «Ждут предоплату».

## 6. «Сформировать → Отправить» прямо в шахматке

В окне создания брони (открывается из шахматки) и в drawer брони — закреплённая панель
действий внизу:

1. **Сформировать** — показывает документ для гостя прямо в этом же окне (справа /
   вкладкой): для неподтверждённой — предложение с условиями, суммой предоплаты и
   сроком опции; для подтверждённой — подтверждение. Всё из п.2: ночи, гости, дети,
   услуги, итог, политика отмены, контакты.
2. **Отправить** — получатель подставлен из профиля (можно изменить), канал email / SMS,
   одна кнопка. После отправки — отметка «Отправлено 10.11 14:32» и история в
   «Коммуникации».

Кнопка всегда в одном месте, основная (primary), подписи глаголами. Этим же закрывается
сценарий КП из CRM.

## 7. Единая логика PMS = CRM

PMS — источник истины; CRM получает изменения через Integration V2 (триггеры по строке
`reservations`). Что выровнять:

| В CRM есть | В PMS сделать | Синхронизация |
|---|---|---|
| `holdExpiresAt`, `confirmedAt` | п.5 (`option_until`, `confirmed_at`) | маппинг полей в проекции CRM |
| Коммерческое предложение (документ + отправка) | п.6 | статус «предложение отправлено» → CRM |
| Inter + синий акцент, светлый фон | п.8 | общая палитра токенов для обеих систем |
| — | возрасты детей, группа | новые поля в проекции брони CRM, CRM показывает их read-only |

Перед правкой проекций — сверка с `docs/CROSS_DATABASE_CONTRACT.md` и
`INTEGRATION_API_V2.md`; изменения контракта только аддитивные.

## 8. Дизайн: цвета, шрифты, размеры

Принципы из разбора современных PMS и экстранетов: нейтральная (не тонированная) база,
один насыщенный акцент для действий, яркие семантические цвета только для статусов
(≤10% площади), высокий контраст текста, крупнее шрифт и цели клика.

- **Токены:** `telivity-*` в Tailwind переводятся на CSS-переменные
  (`rgb(var(--color-…) / <alpha-value>)`) — сотни существующих классов меняют цвет без
  правок по файлам; white-label (`staffPrimaryColor`) переопределяет одну переменную.
- **Палитра (свет):** фон `#F5F6F8`, поверхности белые, текст `#101828`, вторичный
  `#475467`, приглушённый `#667085`, границы `#E4E7EC`, акцент синий `#3657E8`
  (белый текст на нём ≥ 4.5:1). Семантика: успех `#067647/#ECFDF3`, внимание
  `#B54708/#FFFAEB`, ошибка `#B42318/#FEF3F2`, инфо `#175CD3/#EFF8FF`. Бирюзовые
  полупрозрачные заливки убираются.
- **Шрифт:** Inter (кириллица, 400/500/600/700, табличные цифры). Шкала:
  `xs` 13/18, `sm` 14/20, `base` 15/22, заголовки 18–24. Всё, что 9–11px → минимум 12px.
- **Контролы:** высота кнопок и полей 36px (основные действия 40px), радиус 8px,
  карточки 12px, видимый focus-ring 2px; ячейки шахматки шире, плашки контрастнее.
- **Шахматка:** цвет плашки = статус (не подтверждена — штриховка, подтверждена — синий,
  в отеле — зелёный, выехал — серый), долг — красная метка, а не цвет всей плашки.
- **Боковое меню:** тёмное нейтральное (`#101828`) с одним акцентом для активного пункта.
- Проверка: контраст AA по токенам, скриншоты ключевых экранов до/после.

## Решения отеля (2026-11-10)

1. Дети 0–5 занимают место в номере — так и настроены категории по умолчанию (`occupiesBed: true`).
2. Истёкшая опция не снимается автоматически: по умолчанию — напоминание сотруднику. В карточке брони кнопки «Продлить опцию» (+24/48/72 ч или дата), «Напомнить гостю» (предложение с пометкой «Напоминание», email/SMS) и «Снять бронь» вручную (одна или все неподтверждённые комнаты брони).
3. Бронь подтверждает предоплата 50% (`BOOKING_POLICY_DEFAULTS`, отель может изменить в настройках). Пока платёжная система не подключена, кнопка «Предоплата получена» записывает реальный платёж в фолио (наличные, перевод, терминал, номер документа) — при покрытии гарантии бронь подтверждается сразу.

API: `POST /v1/reservations/:id/prepayment`, `PATCH /v1/reservations/:id/option`, `POST /v1/reservations/:id/option/remind`, `POST /v1/reservations/:id/option/release` — все со скоупом `propertyId` и записью в аудит.
